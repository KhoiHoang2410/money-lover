# SemVer versioning, bumped on every PR (pre-1.0 simplified)

The app carries two version numbers: **`MARKETING_VERSION`** — a `MAJOR.MINOR.PATCH` SemVer string (`https://semver.org/`) shown to the owner in the Config footer — and **`CURRENT_PROJECT_VERSION`** — a monotonic build integer for TestFlight/build uniqueness. Every PR bumps both as part of its own diff: the build integer always `+1`, and the SemVer string by the highest-priority change in the branch.

While the app is **pre-1.0** we apply SemVer's §4 allowance and run a *simplified* scheme: a `feat:` commit (or a breaking change) bumps **MINOR**; `fix:`/`chore:`/`docs:`/`refactor:`/`test:` bump **PATCH**; nothing forces a **MAJOR** bump until the deliberate 1.0 release. This maps cleanly onto the Conventional-Commits prefixes the repo already uses, so the bump is derivable from `git log main..HEAD` without a separate decision ritual.

We chose "bump every PR" (rather than batching bumps at release time) because this is a solo, on-device app (ADR-0001) with **no CI and no server-side release pipeline** — there is no other automated moment to attach a version to. Tying the bump to the PR makes the version a checked-in, reviewable fact and guarantees every build the owner installs is distinguishable. The version is read at runtime from the bundle (`AppInfo`), never hard-coded, so the build settings stay the single source of truth.

Because the project is generated by **xcodegen**, `project.yml` is the canonical and *only committed* place for the two settings — `MoneyLover.xcodeproj` is gitignored and each developer regenerates it locally with `xcodegen generate`. The bump is therefore made in `project.yml`; hand-editing the generated pbxproj is the easy mistake (it isn't committed and a regen reverts it) this ADR exists to prevent.

Alternatives rejected:
- **Strict SemVer pre-1.0 (breaking → MAJOR):** would push the app to 1.0.0 on the first breaking change, spending the 1.0 signal before the product is actually stable. The §4 allowance exists precisely for this phase.
- **Manual bumps at release time only:** no releases are cut yet, builds would share a version, and "which build is this?" becomes unanswerable. Rejected for a pre-release, frequently-rebuilt app.
- **Auto-bump via git hook / CI:** no CI exists, and a local hook is invisible in review and easy to skip. A documented PR step keeps the bump explicit in the diff.

## Consequences

- Opening a PR is a four-step procedure (pick bump type from commits, `+1` the build, edit `project.yml` **and** `project.pbxproj`, add a `CHANGELOG.md` entry). Documented in `docs/guidelines/engineering.md` §13 and `CLAUDE.md`; enforced via the Definition of Done.
- The Config footer shows `Money Lover <version> (<build>)` via `AppInfo`, which reads `CFBundleShortVersionString` / `CFBundleVersion` from the bundle.
- `CHANGELOG.md` (Keep a Changelog format) becomes the human-readable history; git log remains the raw record.
- **At 1.0** we switch to strict SemVer (breaking → MAJOR) and supersede this ADR with a follow-up.
- The bump is keyed off Conventional-Commits prefixes, so commit messages must keep using them for the rule to stay mechanical.
